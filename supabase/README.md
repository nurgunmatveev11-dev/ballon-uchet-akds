# Серверная версия: запуск

1. Создайте проект Supabase в корпоративном аккаунте.
2. В SQL Editor выполните `schema.sql`.
3. В разделе Storage создайте приватный bucket `batch-documents` для сертификатов и разрешений.
4. Создайте пользователей через Auth и добавьте их строки в `public.profiles` с одной из ролей:
   `warehouseman`, `operator`, `akds_head`, `skk_head`, `observer`.
5. В SQL Editor выполните `storage-policies.sql`, затем включите MFA для администраторов.
6. Выполните тесты прав для каждой роли: просмотр, приём, партия, выдача, возврат, аннулирование.

Для первого пользователя с ролью начальника СКК после создания в Authentication выполните `assign-skk-head.sql`.
Для начальника АКДС выполните `assign-akds-head.sql`.

Никогда не размещайте `service_role` key в браузерном приложении. Он обходит RLS и должен использоваться только в защищённом серверном коде.

## Сопоставление ролей

| Код | Роль |
|---|---|
| `warehouseman` | Кладовщик |
| `operator` | Оператор |
| `akds_head` | Начальник АКДС |
| `skk_head` | Начальник СКК |
| `observer` | Устаревшая роль; миграция переводит её в `operator` |

## Регистрация по электронной почте

После `four-roles.sql` и `audit-and-documents.sql` примените `registration-and-staff.sql`.
В Supabase Authentication включите обязательное подтверждение электронной почты.
В шаблоне **Confirm sign up** разместите код `{{ .Token }}` (например, `<p>Код подтверждения: {{ .Token }}</p>`).
Новые аккаунты получают неактивный профиль: выбранная при регистрации роль сохраняется как заявка, а доступ включает начальник АКДС после подтверждения почты.
Отключение аккаунта закрывает доступ и сохраняет историю операций.
